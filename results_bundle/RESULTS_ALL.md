### 10. Limitations / what did NOT improve (for the Discussion section)

1. **LSTM confidence is not fixed.** The deep ensemble did worse than MC-Dropout. Both
   signals are near-random (AUROC 0.53–0.56) and their intervals badly under-cover. At 0.85
   the LSTM path auto-executes every decision.
2. **Prophet fix is partial.** Pearson r becomes −0.40 only with context-conditioned
   conformal. Plain split conformal stays wrong (+0.22). Coverage falls 2.5 pp below
   target, and the gain relies on the promo heteroscedasticity the synthetic generator
   builds in.
3. **The ML gate's advantage over a trivial promo/holiday rule is small** on this
   synthetic data. Real-data validation is required before claiming the confidence score
   adds value beyond known calendar flags.
4. **The 0.85 threshold is not optimal.** F1 peaks at 0.80 for XGBoost. The threshold is
   one global value, although the three models' confidence scales differ widely.
5. **The original 77.8 %/22.2 % claim rests on n = 9.** Its two deferred cases were
   accurate forecasts.
6. **The README model comparison mixes pooled and mean-of-series RMSE.** On a like-for-like
   basis Prophet is significantly better than XGBoost.
7. **The ML computation is not verified on-chain** (oracle risk). `shapHash` does not
   hash SHAP output. Approvals are off-chain. Production would need a key-management
   (HSM/KMS) and multisig setup that is not implemented.
8. **Mainnet cost** is prohibitive at 20–100 gwei. L2 figures are scenario arithmetic,
   not measurements.
9. **Scope of the evidence.** All data is synthetic, there is one test window per series,
   and there is no rolling-origin backtest.
10. **Infeasible / not done:** evidential regression for the LSTM (the deep ensemble was
    the method tried). A fresh PlantUML re-render of the diagrams was blocked; the SVGs were
    inspected and text-patched instead. Reproducibility is verified on one OS/Python only.
    Done since the first draft: Solidity coverage (Hardhat), clean-env reproduction, visual
    diagram check, and git history (baseline v1 commit followed by a separate
    contract-hardening commit).

# 2. Task 1 notes: statistical method

*Source: `publication_package/statistical_significance_notes.md`*

## Statistical rigour on forecasting metrics — method notes (Task 1)

Script: `scripts/s02_statistical_significance.py` (inputs cached by `scripts/s01_build_predictions.py`).
Outputs: `statistical_significance.csv`, `statistical_significance_block_sensitivity.csv`,
`statistical_seed_variance_xgboost.csv`, `lstm_seed_variance.csv` (from Task 4), `metric_reproduction_check.csv`.

### What is resampled
Retraining all three models hundreds of times is not cheap (Prophet × 9 series, LSTM × 9
series), so CIs come from a **moving-block bootstrap of the held-out residuals** of the
**saved** model artefacts — the same artefacts whose metrics are cited in the repo. Point
estimates reproduce `models/saved_models/*/metrics.json` to ≤ 1.5e-6
(`metric_reproduction_check.csv`).

* Test sets are each model's own original held-out split: XGBoost 1,233 rows
  (2025-03-18 → 2025-08-01), Prophet 1,278 rows (2025-03-13 → 2025-08-01), LSTM 1,251 rows
  (2025-03-16 → 2025-08-01) (`test_set_spans.csv`).
* Residuals of daily retail forecasts are autocorrelated (weekly cycle), so an i.i.d.
  bootstrap would understate uncertainty. Dates are resampled in **contiguous 7-day blocks**
  (Künsch 1989); all 9 series of a resampled date move together, preserving cross-series
  correlation. B = 2,000 resamples, `numpy.random.default_rng(42)`, percentile 95 % CIs.
* `statistical_significance_block_sensitivity.csv` repeats the aggregate CIs with block
  length 1 (i.i.d.), 7, 14, 28 days.
* Per-series CIs (`series = SKU_x__Region`) are the marginal of the same joint resample.

### Aggregation — an important correction
The README/`model_performance.csv` compares **XGBoost pooled RMSE (7.42)** with
**Prophet/LSTM mean-of-per-series RMSE (6.40 / 14.24)**. These are different statistics:
pooling squares errors across series of very different scale (SKU_A sells ~3× SKU_C), so
pooled RMSE > mean-of-series RMSE for every model. The CSV reports both for every model:
`ALL_pooled` and `ALL_mean_of_series` (MAPE is identical under both because every series
has the same number of test days). Like-for-like, mean-of-series RMSE is XGBoost 6.86,
Prophet 6.40, LSTM 14.27.

### Paired comparisons
Model differences are evaluated on the **137 dates common to all three test sets**
(2025-03-18 → 2025-08-01), with the *same* block resample applied to both models of a
pair (paired bootstrap). Rows `model = A_minus_B`, `metric = rmse_diff / mape_diff`,
`series = ALL_*_common_dates`. A CI excluding 0 indicates a difference at the 5 % level
(no multiple-comparison correction applied; three pairs × two metrics).

### Seed variation (supplementary)
* XGBoost point model retrained with `random_state` ∈ {0,1,2,3,4} (plus the original 42)
  on the identical split (`statistical_seed_variance_xgboost.csv`).
* LSTM: five independently initialised members trained with the unchanged production
  routine (Task 4, `lstm_seed_variance.csv`).
* Prophet's point forecast is a deterministic MAP fit; seeds only affect its sampled
  interval, so no seed study is reported for Prophet's RMSE/MAPE.

### Caveats
* The bootstrap captures sampling variability of the **test period** given fixed trained
  models; seed variation is reported separately and is not folded into the CIs.
* One test window (~4.5 months) per series; no rolling-origin backtest was run.
* The data are synthetic (`data/data_loader.py`, seed 42); the CIs say nothing about
  transfer to real POS data.
* `docs/report_data.json` cites numbers from a different training run than the saved
  artefacts (e.g. LSTM mean RMSE 14.237 vs 14.273; per-series differences up to 0.26);
  all numbers here are for the saved artefacts.

# 4. Task 3 notes: Prophet calibration

*Source: `publication_package/prophet_calibration_notes.md`*

## Prophet confidence recalibration with conformal prediction (Task 3)

Script: `scripts/s03_prophet_conformal.py`; module: `confidence/conformal.py` (new, additive,
unit-tested in `tests/test_conformal.py`; not wired into the live gate).
Outputs: `prophet_calibration_before_after.csv`, `prophet_reliability_by_confidence_bucket.csv`.

### Why Prophet's score points the wrong way
Prophet's 80 % interval width is almost constant within a series (one global
`sigma_obs`), so `relative_width = width / |yhat|` is *smallest on high-`yhat` days* —
which in this data are promo/holiday days, the days with the *largest* errors. Confidence
is therefore highest exactly when the forecast is worst. The reliability table shows it
directly: the top native-confidence quintile has mean APE 5.64 % vs 3.52–3.73 % for the
other four.

### Protocol (no test-period information used)
| window | dates (per series) | used for |
|---|---|---|
| fit | ≤ 70 % date quantile | calibration-stage Prophet (exact production config via `train_prophet_for_series(test_frac=0.30)`); its in-sample residuals train the difficulty models |
| calibration | (70 %, 85 %] | out-of-sample residuals at the same 1–~145-day horizon the production model faces; conformal quantile |
| test | (85 %, 100 %] | **saved production Prophet** forecasts; only window scored |

Difficulty features are flags known at forecast time: `is_promo`, `is_holiday`,
`is_weekend`; residuals are modelled relative to `|yhat|` so one pooled model serves all 9
series. Target coverage 80 % (Prophet's configured `interval_width`); confidence uses the
configured `alpha = 1.0`.

Methods: (1) **split conformal** on |residual| (per series) — constant width; (2)
**normalized split conformal** with s(x) = linear model of |r|/|yhat|; (3) **CQR**
(Romano et al. 2019) with linear quantile regression (q10/q90) of r/|yhat|.

### Result (test set, n = 1,278)
| method | Pearson r(conf, APE) | Spearman ρ | AUROC (low conf → APE>10 %) | coverage (target 0.80) | mean width | series with r < 0 |
|---|---:|---:|---:|---:|---:|---:|
| native interval (before; repo documents +0.250) | **+0.253** | +0.094 | 0.284 | 0.862 | 16.70 | 1 / 9 |
| split conformal | +0.220 | +0.105 | 0.260 | 0.820 | 15.33 | 1 / 9 |
| normalized conformal | **−0.400** | −0.174 | **0.799** | 0.775 | 14.46 | 9 / 9 |
| CQR | −0.392 | −0.123 | 0.765 | 0.773 | 14.80 | 9 / 9 |

(All p < 0.001; exact values and per-series min/max in the CSV.)

### Honest reading
* **Direction fixed, but only by the methods that condition on context.** Plain split
  conformal does *not* fix it (+0.220): it rescales a constant width and cannot create
  heteroscedasticity. That negative result is itself worth reporting.
* The fix works because the difficulty model learns that promo days have ~2.3× the
  relative residual of normal days (fitted coefficient `is_promo = +0.0525` on an
  intercept of 0.0407). **This is exactly the heteroscedasticity the synthetic generator
  injects** (`noise_std × (1 + 1.8·is_promo + 1.2·is_holiday)`), so the improvement is
  partly by construction; on real data the gain depends on how predictable the error
  regime is.
* Rank correlation stays modest (Spearman −0.17). Normalized-conformal confidence takes
  essentially one value per flag combination (the reliability file has only 2 distinct
  quintile bins), so it is a good *detector of hard days* (AUROC 0.80) rather than a
  fine-grained ranking of every forecast.
* **Coverage is 77.5 %, below the 80 % target.** Split conformal's guarantee assumes
  exchangeable calibration/test data; the calibration window (Oct–Mar, incl. festive
  season) and test window (Mar–Aug) differ, and the production model is trained on more
  data than the calibration-stage model. The native interval over-covers (86.2 %).
* At the deployed 0.85 threshold, the share of Prophet decisions cleared for autonomy
  rises from 82.9 % to 92.4 %, and the cleared decisions have lower mean APE (3.67 % vs
  4.13 % under the native interval) — see `gate_baseline_comparison.csv`.
* Neither the live pipeline nor `threshold_config.yaml` was changed; adopting this would
  be a follow-up change.

# 5. Task 4 notes: LSTM uncertainty

*Source: `publication_package/lstm_uncertainty_notes.md`*

## LSTM uncertainty: MC-Dropout vs deep ensemble (Task 4)

Script: `scripts/s04_lstm_uncertainty.py`. Outputs: `lstm_uncertainty_comparison.csv`,
`lstm_seed_variance.csv`.

### Setup
* Same held-out windows for every method: last 15 % of 21-day windows per series, 1,251
  forecasts total.
* **Current approach:** MC-Dropout on the *saved* LSTM models, 30 stochastic passes,
  80 % band = mean ± 1.28·std, `alpha = 0.5` (all from `threshold_config.yaml`).
* **Alternative:** deep ensemble of 5 LSTMs per series (45 models), trained with the
  **unchanged** production routine `train_lstm_for_series(epochs=25)`, seeds 0–4,
  TensorFlow op-determinism on. Uncertainty = std across members' deterministic forecasts.
* Also scored: MC-Dropout on each new member (separates the method from the particular
  weights) and ensemble + MC-Dropout (total variance = between + mean within).
* Evidential regression was not attempted.

### Result
| method | Pearson r(conf, APE) | Spearman ρ | AUROC (APE>10 %) | 80 % interval coverage | mean width | share conf ≥ 0.85 |
|---|---:|---:|---:|---:|---:|---:|
| MC-Dropout, saved models (current; repo documents −0.081) | **−0.105** | −0.135 | 0.549 | 0.233 | 6.83 | 1.000 |
| MC-Dropout, mean over 5 new members (sd of r = 0.015) | −0.091 | −0.133 | 0.553 | 0.228 | 6.66 | 1.000 |
| Deep ensemble (5) | **−0.033** | −0.021 | 0.531 | 0.062 | 1.49 | 1.000 |
| Deep ensemble + MC-Dropout | −0.094 | −0.140 | 0.556 | 0.251 | 7.12 | 1.000 |

### Plain conclusion
* **Neither method gives a strong confidence signal.** MC-Dropout is the better of the
  two (r = −0.105, AUROC 0.549 — barely above the 0.5 of a coin flip); the deep ensemble
  is *worse* (r = −0.033, AUROC 0.531). Combining them does not help. The repo's −0.081
  is reproduced in sign and magnitude (−0.091 to −0.105 here; the repo value came from
  re-trained 15-epoch models with 15 passes and a test-set-selected alpha).
* **The intervals are badly miscalibrated:** the nominal 80 % MC-Dropout band covers
  23.3 % of outcomes; the ensemble band covers 6.2 %. Members trained from different
  seeds converge to nearly the same function (pooled RMSE 15.44–15.57 across seeds), so
  between-member spread (mean width 1.49 units) is far smaller than the actual error
  (RMSE ≈ 15.5).
* **Practical consequence for the gate:** with `alpha = 0.5` every LSTM forecast scores
  ≥ 0.85, so on the LSTM path the deployed gate **never defers** (100 % autonomous at
  0.85, `gate_threshold_sweep.csv`), despite the LSTM having the largest errors of the
  three models (MAPE 7.99 %; 25.6 % of its forecasts exceed 10 % APE).
* Seed study (Task 1 supplement): mean-of-series RMSE across 5 seeds 14.18–14.28
  (saved model 14.27); the 5-member ensemble mean forecast gives 14.20.
* A likely remedy — not run here — is conformal recalibration of the LSTM interval
  (as in Task 3) or a larger `alpha`; both would need validation on held-out data.
* MC-Dropout is itself stochastic: before seeding was fixed (seed set *before* model
  load, TF op determinism on), three runs of the identical 30-pass procedure gave
  r = −0.1056, −0.1090 and −0.1048, i.e. Monte-Carlo noise of about ±0.004 in r. The
  reported −0.105 is the now-deterministic seeded value.

## Security / Threat-Model Review — `ReplenishmentLedger.sol`

Scope: `blockchain/contracts/ReplenishmentLedger.sol` (v1 as found, kept verbatim at
`blockchain/legacy/ReplenishmentLedger_v1.sol` + `.json`) and the off-chain bridge

`publication_package/gas_measurements.csv`.

### Summary of findings

| # | Finding (v1) | Severity | Status in v2 | Test |
|---|---|---|---|---|
| F1 | `logDecision()` and `autoExecutePO()` callable by **any** address | High | Fixed: `onlyAuthorizedCaller` (owner-managed allow-list; deployer authorised in constructor) | `test_log_decision_rejects_unauthorized_caller`, `test_auto_execute_po_rejects_unauthorized_caller`, `test_owner_can_grant_and_revoke_callers`, `test_non_owner_cannot_administer` |

| F6 | Confidence-score oracle: the contract trusts whatever confidence the backend sends | High (architectural) | **Not fixed — inherent limitation of the design**; see section below | `test_v1_contract_had_no_access_control_or_double_spend_protection` shows the v1 exposure |

Before/after evidence: `test_v1_contract_had_no_access_control_or_double_spend_protection`
deploys the original v1 bytecode and shows a never-authorised account logging an
AUTONOMOUS record with confidence 0.10 and threshold 0.0 and then executing **two** POs
for it. Every step of that sequence reverts on v2.

Non-regression: `test_interact_bridge_works_unchanged_against_v2` drives the unchanged
`interact.log_decision()` / `interact.execute_po()` against v2. The ABI of
`logDecision`/`autoExecutePO`, both structs, and all three original events are unchanged,
and `deploy.py` still calls the zero-argument constructor from `accounts[0]` (which
becomes owner and authorised caller), so `pipeline.py`, the FastAPI routers, the
dashboard and `ledger_integrity_check.py` work without modification.

### (a) Access control

**v1:** no modifier on either state-changing function. Anyone with RPC access to the
chain could (i) append arbitrary decision records — polluting the audit trail that
the project presents as its trust anchor — and (ii) trigger PO execution for any
AUTONOMOUS record, any number of times.

**v2:** `owner` (set to `msg.sender` at deployment), `authorizedCallers` mapping,
`onlyOwner` admin functions (`setAuthorizedCaller`, `transferOwnership`,
`setMinAutonomousThreshold`), and `onlyAuthorizedCaller` on `logDecision` and
`autoExecutePO`. Admin actions emit `OwnershipTransferred`,
`CallerAuthorizationChanged` and `MinAutonomousThresholdChanged` events, so changes
to who may write are themselves part of the audit trail.

Residual risk: single-key ownership. A production deployment should put `owner`
behind a multisig or timelock; the backend's signing key should live in an HSM/KMS
rather than in Ganache's unlocked `accounts[0]` (which `interact.py` uses today).

### (b) Reentrancy

`autoExecutePO()` performs `require` checks, then writes storage
(`_nextPOId`, `poForDecision`, `purchaseOrders`, `poIds`), then emits an event.
There is no `call`, `transfer`, `send`, `delegatecall` or external contract
invocation anywhere in the contract, so there is no re-entry point. In v2 the
state write that closes the double-execution hole (`poForDecision`) happens before
anything else, and a `nonReentrant` lock wraps the function anyway. Measured gas
overhead of all v2 checks together: +3,939 gas per `logDecision` (+1.3 %) and
+26,842 gas per `autoExecutePO` (+11.7 %, dominated by the new
`poForDecision` SSTORE); see `gas_cost_analysis.md`.

### (c) The confidence-score oracle risk

The confidence score that decides whether a PO is executed autonomously is computed
**off-chain** (Python, `confidence/confidence_estimator.py`) and passed to the
contract as a plain `uint256` argument. The contract cannot tell a confidence of
0.91 that came from `exp(-alpha * (q90 - q10)/|yhat|)` from a value typed in by an
attacker.

**Attack:** an adversary who compromises the backend host, its signing key, or
any component between the model and `interact.log_decision()` (the YAML config,
the saved model files, the Python process) can submit
`logDecision(status = AUTONOMOUS_EXECUTION, confidenceScore = 0.99e18,
confidenceThreshold = 0.85e18, orderQuantity = <anything>)` and then
`autoExecutePO(id)`. Every on-chain check passes. The PO is executed and the ledger
records — immutably and convincingly — a high-confidence, policy-compliant decision
that never happened. Immutability makes the forgery *harder to repair*, not
easier to detect.

**What v2 does mitigate**
- Only allow-listed addresses can write (so an attacker needs the backend key, not
  just RPC access).
- At most one PO per logged decision (no replay amplification of a single forged
  record).
- The autonomy policy cannot be weakened from the backend: an AUTONOMOUS record must
  satisfy `confidence ≥ threshold ≥ minAutonomousThreshold`, and only the owner can
  lower the floor (an on-chain, evented action). Lowering `CONFIDENCE_THRESHOLD` in
  `threshold_config.yaml` below 0.85 will now make AUTONOMOUS logs revert until the
  owner changes the floor — a deliberate behaviour change, documented here.

**What this project does NOT implement (state explicitly in the paper)**
- **No on-chain or cryptographic verification of the ML computation.** The contract
  does not, and cannot, check that the confidence value was produced by the stated
  model on the stated inputs. There is no zkML proof, no TEE attestation, no
  committee/multi-oracle agreement, and no commitment to model weights or input
  features.
- **No binding of the record to its inputs.** Neither the feature vector, the
  model version/hash, nor the prediction interval bounds are stored or hashed
  on-chain, so a decision cannot be independently recomputed from chain data alone.
- **`shapHash` is not a SHAP hash (finding F5).** `interact._shap_hash()` hashes
  `record.confidence_metadata`, which for XGBoost is the constant
  `{"quantiles": [0.1, 0.9]}` — every XGBoost decision therefore carries the *same*
  32-byte value. `explainability/shap_explainer.hash_explanation()` exists but is
  not called anywhere on the decision path. The claim in
  `docs/novelty_and_contribution.md` §3.4 that "SHAP explanations … are hashed and
  stored on-chain with every decision record" is not true of the current code.
- **No order-quantity bound.** `orderQuantity` is accepted as given; a per-SKU cap
  or rate limit is not enforced on-chain.
- **Human-approval path is off-chain only.** `POST /approvals/{id}/approve` returns
  a JSON note; there is no on-chain approval transaction or approver signature.

**Mitigations a deployment would need (future work, not implemented)**
1. Hash-commit the full decision context (feature vector, model artefact hash,
   interval bounds, the real SHAP payload via `hash_explanation()`) in
   `logDecision`, so any record can be recomputed and audited off-chain.
2. Signed model outputs from an attested enclave (TEE) or k-of-n independent
   inference oracles, verified in the contract before `autoExecutePO`.
3. zkML proofs of inference for the (small) XGBoost quantile models — feasible
   in principle for tree ensembles, at substantial proving cost.
4. On-chain per-SKU quantity caps / daily spend limits and a timelock between
   `logDecision` and `autoExecutePO` during which a guardian can veto.
5. Multisig owner; HSM-held backend key; a real `approveAndExecute()` function
   requiring an approver signature for HUMAN_APPROVAL records.

#### What makes this different from prior work

| Prior Approach | Our Approach |
|----------------|-------------|
| ML produces a forecast; a separate system decides what to do with it | ML confidence *directly determines* whether the smart contract is authorized to act autonomously |
| Explainability is a post-hoc reporting tool | SHAP explanations are hashed and logged on-chain alongside every decision, making the audit trail explain *why* as well as *what* |
| Blockchain records *that* a transaction happened | Blockchain records the full decision context: forecast, confidence, explanation hash, SS/ROP metrics, and the reasoning for the gate outcome |

**The key architectural interlock:**

```
Forecast Confidence >= 0.85  -->  Smart Contract auto-executes PO
Forecast Confidence <  0.85  -->  Ledger logs + flags for human review
```

This is not a simple threshold applied to a forecast. The confidence score itself is derived from three different uncertainty quantification methods (quantile regression for XGBoost, native intervals for Prophet, MC-Dropout for LSTM), normalized into a single comparable scale. **ML decides whether blockchain is trusted to act autonomously.** This is the structural connection that closes the Review-1 gap.

---

### 3. Technical Contributions

#### 3.1 Tri-Model Forecasting with Unified Confidence Scoring

Three fundamentally different ML architectures are trained on the same data:

| Model | Confidence Signal | Method |
|-------|------------------|--------|
| XGBoost | Prediction interval width | Quantile regression (q10/q90 models) |
| Prophet | Native uncertainty interval | Built-in yhat_lower/yhat_upper |
| LSTM | Predictive variance | MC-Dropout (30 stochastic forward passes) |

All three are normalized to a single 0-1 confidence score using:
```
confidence = exp(-alpha * interval_width / |forecast|)
```

This enables the Decision Gate to threshold uniformly regardless of which model produced the forecast. The calibration of `alpha` per model was empirically validated (see `confidence/calibrate.py`).

#### 3.2 Confidence-Gated Decision Engine

The Decision Gate (`decision_gate/gate.py`) is deliberately minimal — it does not re-derive confidence or reorder need. It only routes:

- **NO_ACTION**: Stock sufficient, no reorder needed (regardless of confidence)
- **AUTONOMOUS_EXECUTION**: Reorder needed + confidence >= 0.85 → smart contract auto-executes PO
- **HUMAN_APPROVAL**: Reorder needed + confidence < 0.85 → logged on-chain, flagged for human review

This separation is what makes the "where's the ML" answer clean: ML (confidence) decides whether autonomy is *allowed*; the gate decides what happens as a result; the blockchain only executes/records what the gate decided.

#### 3.3 Blockchain Audit Ledger

The `ReplenishmentLedger.sol` smart contract stores:

- **DecisionRecord**: SKU, region, model type, forecast value, confidence score, SHAP explanation hash, execution status, timestamp
- **PurchaseOrder**: Linked to the originating decision, with order quantity and execution status

Every decision is logged regardless of outcome (immutable audit trail). When the confidence gate passes, `autoExecutePO()` is called to execute the PO on-chain. The contract emits `DecisionLogged`, `OrderExecuted`, and `HumanApprovalRequired` events for off-chain monitoring.

#### 3.4 Explainability-on-Chain

SHAP explanations for XGBoost forecasts are hashed (SHA-256) and stored on-chain with every decision record. This means:

1. The audit trail explains *why* a forecast was made (feature contributions)
2. The hash is tamper-evident (any modification changes the hash)
3. The original explanation can be verified by recomputing the hash off-chain

For Prophet, the native decomposition (trend + seasonality + holiday effects) is available off-chain. For LSTM, attention weights approximate feature importance. All three are surfaced in the dashboard.

### Abstract

This paper presents a supply chain replenishment system that combines multi-model machine learning forecasting, explainable AI (XAI), and blockchain-based audit logging into a unified autonomous pipeline. The core novelty is a **confidence-gated decision engine** where ML confidence scores directly determine whether a blockchain smart contract is authorized to execute purchase orders autonomously. - **Trust**: Stakeholders cannot verify why a reorder was triggered or whether the decision was sound
- **Auditability**: Inventory decisions leave no immutable trail; errors or manipulation are undetectable

#### 1.3 Contribution

This work addresses all three gaps through a structurally unified pipeline where:
1. ML forecasting produces demand predictions with uncertainty quantification
2. Explainability modules (SHAP, decomposition, attention) clarify why each forecast was made
3. A confidence-gated decision engine determines whether the smart contract is trusted to act
4. An immutable blockchain ledger records every decision with its full context

### 3. System Architecture

#### 3.1 Pipeline Overview

The system comprises eight interconnected stages:

1. **Data Layer**: Synthetic sales, promotion, and holiday data for 3 products (SKU_A, SKU_B, SKU_C) across 3 regions (North, South, West), totaling 9 time series with 800+ daily observations each.

2. **Tri-Model Forecast Engine**: Three fundamentally different ML architectures trained on the same data:
   - **XGBoost**: Gradient boosted trees with quantile regression for prediction intervals
   - **Prophet**: Facebook Prophet with native decomposition and uncertainty intervals
   - **LSTM**: Recurrent neural network with additive attention and MC-Dropout

3. **Explainability Layer**: Model-specific explanation generation:
   - SHAP values for XGBoost (feature contribution attribution)
   - Prophet native decomposition (trend + seasonality + holiday effects)
   - LSTM attention weights (temporal importance approximation)

4. **Confidence Estimation Module**: Normalizes uncertainty signals from all three models into a single 0-1 score using exponential decay: `confidence = exp(-alpha * interval_width / |forecast|)`

5. **SS/ROP Inventory Calculator**: Computes Safety Stock and Reorder Point using standard inventory control formulas.

6. **Decision Gate**: Three-way routing based on reorder need and confidence threshold.

7. **Blockchain Audit Ledger**: Solidity smart contract on Ganache recording all decisions immutably.

8. **Backend + Dashboard**: FastAPI REST API and Streamlit UI for monitoring and interaction.

#### 3.2 Confidence-Gated Decision Engine

The Decision Gate is the structural bridge between ML and blockchain:

```
reorder_required = (current_inventory <= reorder_point)

if NOT reorder_required:
    decision = NO_ACTION
elif confidence >= threshold:
    decision = AUTONOMOUS_EXECUTION  ->  smart contract auto-executes PO
else:
    decision = HUMAN_APPROVAL        ->  logged on-chain, flagged for review
```

This is deliberately minimal — the gate does not re-derive confidence or reorder need. It only routes based on two independent module outputs, keeping the ML integration clean and auditable.

### 4. Methodology

#### 4.1 Forecasting Models

**XGBoost** (400 trees, max_depth=5, learning_rate=0.05):
- Point model: `reg:squarederror` objective
- Quantile models: `reg:quantileerror` with alpha=0.1 and alpha=0.9
- Features: 7-day/14-day/30-day lags, rolling mean/std, day-of-week, month, is_promo, is_holiday

**Prophet** (per-series, additive seasonality):
- Weekly + yearly seasonality
- Public holidays as extra regressors
- is_promo as additional regressor
- 80% uncertainty interval (native yhat_lower/yhat_upper)

**LSTM** (48-unit LSTM + Bahdanau attention + MC-Dropout):
- Input: 21-day rolling window of scaled sales
- Attention layer: additive (Bahdanau-style) over LSTM timesteps
- MC-Dropout: 30 stochastic forward passes for uncertainty estimation
- Confidence: z_multiplier=1.28 (80% CI half-width)

#### 4.2 Confidence Scoring

All three models' uncertainty signals are normalized to a single 0-1 score:

```python
relative_width = interval_width / max(|point_forecast|, eps)
confidence = exp(-alpha * relative_width)
```

Per-model alpha values are calibrated empirically:
- XGBoost: alpha=1.0 (confidence-error correlation: -0.346)
- Prophet: alpha=1.0 (correlation: +0.250 — homoscedastic by construction, documented limitation)
- LSTM: alpha=0.5 (correlation: -0.081)

#### 4.3 Inventory Control

Standard safety stock formulas from operations research:

```
Safety Stock (SS)   = Z * sigma_d * sqrt(L)
Reorder Point (ROP) = (D_daily * L) + SS
```

Where Z=1.645 (95% service level), L=7 days lead time, sigma_d = trailing 90-day std of actual sales.

#### 4.4 Blockchain Layer

**Smart Contract** (`ReplenishmentLedger.sol`):
- `DecisionRecord` struct: SKU, region, order quantity, model type, forecast, confidence, threshold, SHAP hash, status, timestamp
- `PurchaseOrder` struct: linked to decision, with quantity and execution status
- `logDecision()`: called for every decision (immutable audit trail)
- `autoExecutePO()`: called only when confidence gate passes
- Events: `DecisionLogged`, `OrderExecuted`, `HumanApprovalRequired`

**Fixed-point encoding**: All float values encoded as uint256 with 1e18 precision (standard Solidity convention).

### 9. Limitations and Future Work

1. **Prophet confidence calibration**: The homoscedastic uncertainty interval limits Prophet's confidence signal. Future work could explore Bayesian Prophet or conformal prediction.

2. **Single threshold**: The 0.85 threshold is empirically tuned. Adaptive thresholds per model or product could improve gate accuracy.

3. **Synthetic data**: Results are on synthetic sales data. Real-world validation with actual inventory feeds is needed.

4. **Smart contract scope**: The current contract handles simple PO execution. Production systems would need multi-signature approval, escrow, and supply chain integration.

5. **LSTM confidence**: The weak confidence-error correlation (-0.081) suggests LSTM's MC-Dropout uncertainty is not well-calibrated. Ensemble methods or evidential deep learning could improve this.

This work demonstrates that machine learning can structurally govern blockchain behavior through confidence-gated decision routing. The system achieves 77.8% autonomous execution while maintaining a human-approval safety net for uncertain decisions. All decisions — including model explanations — are immutably recorded on-chain, creating a verifiable audit trail that explains *why* as well as *what*. The confidence-gated architecture provides a principled bridge between ML uncertainty quantification and blockchain authorization, closing the identified gap between forecasting and inventory action.
